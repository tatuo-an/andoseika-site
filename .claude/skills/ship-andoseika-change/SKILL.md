# andoseika-siteの変更を出荷する

このリポジトリはコードの変更が起きるたびに「型チェック→ビルド確認→コミット→プッシュ」という同じ流れを踏む。毎回イチから考えず、このスキルの手順をそのまま実行する。

## なぜこの手順が必要か

- **型チェックとビルドを両方見る**: `tsc --noEmit` は型エラーしか拾わない。Next.jsのビルドはそれとは別に、サーバー/クライアントコンポーネントの境界違反や存在しないモジュール参照など、型チェッカーが見ない種類のエラーを検出する。どちらか片方だけでは不十分。
- **pushの前に必ずfetchする**: このリポジトリは複数のセッション（別のClaudeの会話や人間）が並行して同じ`main`にpushしていることが多い。fetchせずにpushすると単純に失敗するし、気づかずに古い前提でコミットを作ると後でコンフリクトが面倒になる。
- **変更したファイルだけを明示的にadd**: `git add -A` や `git add .` は使わない。他のセッションが同じ作業ディレクトリに未コミットの変更を残していることがあり（進行中の別タスクを巻き込んで壊す・意図しないファイルを混入させるリスクがある）、自分が触ったファイルだけを名指しでaddする。

## 手順

1. **型チェック**
   ```
   cd "C:\Users\user\Desktop\andoseika-site" && npx tsc --noEmit -p tsconfig.json
   ```
   出力が何もなければ通過。エラーが出たら直してからやり直す。

2. **ビルド確認**
   ```
   npm run build
   ```
   `/api/chat`が`OPENAI_API_KEY`未設定で`Failed to collect page data for /api/chat`エラーを出すのは既知の問題（ローカル環境にキーが無いだけで、本番のVercelには設定済み）。このエラー**だけ**なら無視してよい。それ以外のエラーが出たら原因を直す。

3. **リモートの状態を確認**
   ```
   git status -s
   git fetch origin
   git log origin/main --oneline -3
   ```
   `git status -s`で今回の変更ファイルを把握し、他セッションの未コミット変更を巻き込まないようにする。`fetch`+`log`でリモートが自分のローカルより進んでいないか確認する。

4. **変更したファイルだけをadd してコミット**
   自分が編集したファイルパスを明示的に指定する。コミットメッセージは日本語で、何をなぜ変えたか一言添える。末尾に必ずこのトレーラーを付ける:
   ```
   git add <変更したファイルを列挙>
   git commit -m "$(cat <<'EOF'
   <変更内容の要約（日本語、1〜3行）>

   Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>
   EOF
   )"
   ```

5. **リモートが進んでいたらrebase**
   手順3で`origin/main`が自分のローカルより先に進んでいた場合のみ:
   ```
   git pull --rebase origin main
   ```
   コンフリクトが出たら中身を確認して解決する（`--no-verify`や強制的な上書きで済ませない）。

6. **push**
   ```
   git push origin main
   ```

## 注意点

- 6を実行する前に、リポジトリ内に**このタスクと無関係な大量の未コミット変更**（例: 別の大きな移行作業の途中経過）が無いか`git status -s`で確認する。あれば自分が編集したファイル以外は絶対に巻き込まない。
- ブランチが`main`以外（例: 進行中の別タスク用ブランチ）にいる場合は、そのブランチ名に合わせて`push origin <ブランチ名>`にする。`git branch --show-current`で確認してから決める。
- コミット後は、ユーザーに確認を取らずそのままpushまで進めてよい（過去のフィードバックで確認済みの運用）。
